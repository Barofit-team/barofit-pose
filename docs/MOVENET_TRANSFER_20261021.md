# MoveNet Lightning → 기존 판정 엔진 비교

2026-10-21. 기본 MediaPipe 모델과 기존 운동 판정 코드는 유지했다. 이번 추가는 오프라인 비교용 추출기·입력 변환기·실행 예제다.

## 비교 구성

푸쉬업·플랭크·버드독·점핑잭 각 4개, 총 16개 기존 영상 구간을 실행했다. 각 모델에 같은 프레임·크기·시간을 입력했다. 최대 20fps, 너비 최대 640px. 원본이 15fps이면 15fps 그대로 사용한다. 모든 모델에 같은 JS Analyzer의 기본 설정을 적용했다.

| 구분 | 영상 입력 | 판정에 전달하는 신뢰도 |
|---|---|---|
| MediaPipe Full | 기존 VIDEO 모드 | 기존 visibility / presence |
| MoveNet Lightning 기본 비교 | 전체 화면을 정사각 패딩 | 원시 score를 두 품질 필드에 복사 |
| MoveNet Lightning 크롭 비교 | 이전 프레임의 관절로 인물을 추적해 크롭 | 원시 score를 두 품질 필드에 복사 |
| 별도 민감도 실험 | 동일한 추적 크롭 결과 재사용 | 원시 0.3이 기존 0.5 문턱에 해당하도록 단조 변환 |

**MoveNet score와 MediaPipe visibility/presence는 같은 확률이 아니다.** 기본 비교는 기존 엔진에 그대로 연결했을 때의 호환성 평가다. 같은 숫자 0.5를 사용했다고 두 모델의 공정한 최적 정확도를 비교한 것은 아니다. 민감도 실험의 0.3도 보정 완료 값이나 권장 운영값이 아니다.

크롭은 [TensorFlow 공식 MoveNet 예제](https://www.tensorflow.org/hub/tutorials/movenet)의 이전 관절 기반 영역 계산을 참고했다. OpenCV로 재샘플링했으므로 TensorFlow 연산과 비트 단위로 같은 구현은 아니다. 다음 프레임이나 정답 영역을 사용하지 않았다. 시간 필터는 기존 판정 엔진의 것만 사용했다.

## 좌표 연결

`runtime/adapters/movenet.js`는 원본 화면 좌표계의 17개 `[y,x,score]`를 기존 33슬롯 입력으로 변환한다. 이번 네 운동이 사용하는 어깨·팔꿈치·손목·골반·무릎·발목은 직접 대응한다. 손가락·발끝 등 없는 좌표는 null/품질 0으로 둔다. z=0은 2D 엔진 입력 호환용이며 깊이 추정값이 아니다. 원시 score를 올리는 동작은 기본 변환기에 없다.

## 대표 결과

| 영상 | MediaPipe | MoveNet 전체 | MoveNet 크롭 | 크롭 + 진단용 0.3 |
|---|---:|---:|---:|---:|
| 푸쉬업 P2 정상 | 12회 | 0회 | 2회 | 12회 |
| 푸쉬업 P2 오류 | 12회 | 0회 | 7회 | 13회 |
| 푸쉬업 P5 정상 | 9회 | 0회 | 0회 | 0회 |
| 푸쉬업 P5 오류 | 6회 | 4회 | 2회 | 8회 |
| 플랭크 P2 유효 유지 | 14.90초 | 0초 | 9.13초 | 14.90초 |
| 플랭크 무릎 오류 유효 유지 | 8.50초 | 1.47초 | 3.37초 | 2.77초 |
| NHS 버드독 | 1회 / 7.91초 | 0회 / 0초 | 1회 / 7.77초 | 1회 / 8.07초 |
| NASM 점핑잭 | 4회 | 0회 | 4회 | 4회 |
| Kickstand 점핑잭 | 19회 | 0회 | 0회 | 2회 |

플랭크 시간은 모든 필수 항목이 정상인 유효 유지 시간, 버드독 시간은 오류 여부와 별개인 동작 유지 관측 시간이다. 서로 같은 뜻으로 합산하지 않는다. 버드독 일부 클립은 펼친 자세에서 시작해 복귀까지 완성하지 않아 두 모델 모두 카운트 0인 경우가 있다.

### 피드백에서 확인한 차이

- P2 오류 푸쉬업: MediaPipe 골반 처짐 회차 경고 10회, MoveNet 크롭 3회. 진단용 0.3에서는 12회와 복귀 경고 1회로 변했다. 카운트·평가 가능한 회차 수도 달라 경고 수만으로 정확도를 비교할 수 없다.
- P5 오류 푸쉬업: 기존 모델은 골반 올라감·팔꿈치 굽힘 부족·상체 이동 부족을 출력했다. MoveNet 크롭은 회차 평가 보류가 많았고, 0.3 실험에서는 같은 종류의 경고가 나왔지만 횟수는 6회 대 8회로 달랐다.
- 플랭크 무릎 오류: 두 모델이 골반 올라감·무릎 굽힘을 출력했지만 MoveNet은 경고 구간이 길어 유효 유지 시간이 줄었다. 좌표 위치와 항목별 판정 가능 구간이 모두 영향을 준다.
- NHS 버드독: 추적 크롭에서는 카운트·유지 시간이 비슷하고 두 모델 모두 경고 없음. 반면 다리 과상승 시범에서는 유지 단계와 좌우 항목별 관측 범위가 달라 일부 경고가 빠졌다.
- NASM 점핑잭: 추적 크롭은 4회·무경고로 일치. 다른 영상은 발목 등의 점수가 흔들리며 동작 기록이 끊겼다. 팔·다리 반대 움직임 영상에서 기존 협응 경고가 MoveNet에서는 나오지 않았다.

검토한 정지 장면: P2/P5 푸쉬업 5·9초에서 MoveNet 팔꿈치·손목 등의 점수가 문턱 아래로 내려가 판정이 보류됨. 버드독 과상승 9초에서는 뻗은 다리 좌표가 보이더라도 엔진이 유지 단계로 분류하지 않아 해당 시점 경고가 없음. 점핑잭 Kickstand 5초에서는 한쪽 발목이 품질 문턱 미달임. 회색 뼈대는 이 낮은 품질 좌표를 표시한다.

## 해석

Lightning은 이번 CPU 실행에서도 빠르지만 **기존 판정 엔진의 즉시 대체 모델로는 아직 적합하지 않았다.** 크롭과 모델별 품질 처리가 중요하며 단순히 문턱을 낮추는 것으로 모든 문제가 해결되지 않았다. 기본 MediaPipe는 유지한다.

이는 MoveNet 자체의 일반적인 정확도 순위가 아니다. 정답 관절·전 회차 수동 라벨이 없는 소규모 호환성 실험이며 MediaPipe 출력도 정답이 아니다. Mendeley 정상 파일에서도 기존 모델의 골반 경고가 나왔으므로 파일명만으로 오경고 여부를 확정하지 않았다. 모델별 최적화·Android 실행·독립 검증은 이번 범위에 포함하지 않았다.

푸쉬업 원본에는 배경 인물이, Kickstand 영상에는 거울 반사가 포함된다. 같은 입력으로 비교했지만 이 결과를 단일 사용자만 촬영한 서비스 환경의 성능으로 일반화하지 않는다.

검증: 기존 runtime 17개 파일의 해시 동일, JS 테스트 58개 통과, 동일 시간축의 실시간 결과 20,196개·세트 결과 64개 규격 검증. 비교 영상 16개와 품질 민감도 영상 4개의 디코딩·시간 길이를 확인했다. 선택한 프레임의 뼈대·표시는 직접 확인했으며 브라우저 내부 재생 조작은 검증하지 않았다.

세트 결과에서 부동소수점 연산으로 준수율이 `100.00000000000001`인 사례가 있었다. 비교 예제의 JSON 내보내기에서만 1e-9 미만의 범위 초과를 100으로 정리하고 `_set_raw.json`에 원본을 보존했다. 판정 엔진 내부 값과 카운트·시간·경고는 변경하지 않았다.

## 재실행

영상 추출에는 OpenCV, NumPy, MediaPipe, LiteRT(또는 TensorFlow)가 필요하다. 기본 설치에 새로운 런타임을 강제로 추가하지 않았다. 실행 폴더를 기준으로 manifest의 영상 경로를 맞춘다.

```sh
python -m analysis.model_comparison.extract cases.json --output results/transfer --mediapipe models/pose_landmarker_full.task --movenet models/movenet_lightning.tflite --dynamic-crop
node examples/compare_pose_models.mjs cases.json results/transfer --sensitivity
```

각 구간 폴더에 입력 JSONL, 기존 v2 실시간 결과 JSONL, 세트 JSON, 추출·판정 처리 시간이 남는다. `--sensitivity`를 빼면 품질 변환 실험은 하지 않는다. 기본 모델 등록과 운동별 판정·임계값·반환 규격은 수정하지 않았다.
